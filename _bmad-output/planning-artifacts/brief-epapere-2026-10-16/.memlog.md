- (event) Session started: Create intent confirmed for e-Papere SMS/LMS brief. User provided comprehensive initial context including problem, solution, tech stack, and MVP boundaries.
- (decision) Tech stack fixed by user: React+TypeScript+Vite+Tailwind (FE), Node.js+Express+TypeScript (BE), MongoDB+Mongoose (DB). Non-negotiable.
- (decision) Payment workflow: dual-lane confirmed. Primary = student self-service portal upload. Fallback = admin-assisted entry. Long-term goal is full self-service; WhatsApp remains supplementary comms only.
- (decision) Scale: actual enrollment figures not confirmed. Architecture planned against 3 scenarios: 200 / 2,000 / 10,000 students. Modular monolith, no premature microservices. Perf targets deferred to post-enrollment-confirmation.
- (decision) Video delivery: Zoom stays as external integration for MVP. Provider-independent class session model (manual entry of meeting details). No Zoom API automation in MVP. No in-house video infra.
- (decision) Subject management: dynamic DB-driven, not hardcoded. 4 initial subjects (Math, Science, Sinhala, ICT). Admin CRUD for subjects without code changes. All modules must accommodate new subjects dynamically.
- (decision) User model: separate student and guardian identities with linked profiles. Guardian manages multiple children from one account. Students own learning access; guardians own financial/admin. Not a shared family account.
- (decision) Course model: persistent enrollment + separate monthly billing/access entitlements. Course is grade+subject+teacher+category combo. Not recreated monthly. Non-payment restricts access, does not delete account or enrollment history.
- (decision) Student ID: auto-generated by backend at registration (EP-000001 format), before payment, unique+permanent, same process for self and admin-assisted. Not tied to grade/subject/status. Never reassigned.
- (decision) Reporting scope: operational dashboards only. Role-segmented: Owner (revenue/enrollment overview), Finance (payment verification queue), Admin (student/access status), Teacher (own course roster). No advanced analytics in MVP.
- (decision) Primary success criterion: eliminate monthly WhatsApp group creation. Payment verified -> course access auto-activated without admin manual enrollment step. 3-month target window.
- (assumption) Historical content access policy after non-payment not defined by user. Flagged as open decision for institute to approve - not invented in brief.
- (decision) Grade range confirmed: MVP supports Grades 6-11 only. Grades 1-5 and 12-13 excluded from MVP but architecture must support future expansion. Dynamic DB-driven grade management, not hardcoded.
- (decision) Student grade progression: student retains EP ID across grade changes. Historical enrollments, payments, and records preserved. Grade change does not require new account.
- (decision) Notifications MVP: in-app only (dashboard). No automated SMS/WhatsApp/email in MVP. Admin uses manual WhatsApp with copyable message templates as fallback. Architecture separates events from delivery channels for future integration.
- (decision) Institute is live and operating. Migration required: incremental 5-stage transition. Manual onboarding + bulk import utility. Duplicate detection mandatory. Imported payments not auto-verified - require reconciliation evidence.
- (decision) Migration audit trail required. Failed imports must be reviewable and correctable. Migration must not create duplicate students, enrollments, invoices, or payments.
- (assumption) Historical content access policy (what a student can access after non-payment for a month) not confirmed. Flagged as open business decision for institute to define before PRD.
- (assumption) Whether Grade 11 students (16-17yo) can self-register without guardian involvement not confirmed. Flagged as open policy decision for institute.
